# Agent Notes

This repository contains Marlin firmware and OrcaSlicer presets for a DIY Graber i3 style printer named `StarGraber`.

## Printer Context

- Board: MKS TinyBee
- Marlin `PRINTCOUNTER` is enabled with a top-level LCD information menu. The idle status line shows accumulated print time, with reminders to check/tighten screws every 100 print hours and lubricate the motion system every 200 print hours. `PRINTCOUNTER_SAVE_INTERVAL` is `0`, so statistics save at job end without periodic EEPROM writes that could disrupt the TinyBee's I2S stepper stream.
- Current configured nozzle-to-probe offset: `{ 21, -17, -1.93 }`.
- The active `StarGraber` Orca end G-code parks at `X10 Y195`, corresponding to `Y_MAX_POS - 5` with the firmware's `Y_MAX_POS` of `200`, so the bed is presented toward the user.
- Marlin's `NOZZLE_PARK_FEATURE` is enabled with `NOZZLE_PARK_POINT { 10, (Y_MAX_POS - 5), 10 }`, and `EVENT_GCODE_SD_ABORT` runs `G27` so stopping an SD print uses that park point instead of homing XY.
- Firmware constraint: do not recommend `LIN_ADVANCE`; this board/setup does not support it in the user's environment.
- The repo owner is the only user of this repository, so tracking live OrcaSlicer user presets is intentional.
- `mks_tinybee` builds with `ESP3D_WIFISUPPORT` should keep `AsyncTCP` pinned to `me-no-dev/AsyncTCP@3.3.2` and `ESP Async WebServer` pinned to `sbkila/ESP Async WebServer@1.2.3`; newer unpinned packages can break against the old ESP32 Arduino core with missing watchdog config symbols such as `CONFIG_ESP_TASK_WDT_TIMEOUT_S`.

## Orca / Preset Context

- Track both `orca/OrcaSlicer/system/Custom/` and `orca/OrcaSlicer/user/default/` because they contain the real working machine, filament, and process presets.
- Keep bundled stock Orca filament library content ignored unless there is a specific reason to version it.
- For Orca's native `ESP3D` print host, set `print_host` to the bare host or IP without `http://`; use `print_host_webui` for the full browser URL if you want one-click access to the web interface as well.
- Current `StarGraber` ESP3D workflow assumes web authentication is disabled; Orca's ESP3D integration may not work correctly if the web UI requires login.
- Tested on 2026-03-29: Orca's built-in `ESP3D` `Upload and Print` path reached the printer but did not leave the uploaded file visible on the Marlin SD card. Marlin then failed `M23` with `open failed` for the expected 8.3 filename, and `M20 L` over ESP3D websocket confirmed the file was not present in the SD listing afterward.
- Live ESP3D probing on 2026-03-29 showed this TinyBee setup is using ESP3D's direct-SD `/upload` route, not the `/upload_serial` route that Orca hardcodes for `ESP3D`. The working browser UI creates directories and uploads to SD through `/upload`, and its print button sends `M23 <current_path><filename>` followed by `M24`.
- `StarGraber` now uses a local helper, [`tools/orca_esp3d_up_and_p_proxy.py`](/home/fopor/Software/marlin/Marlin-2.1.3-b2/tools/orca_esp3d_up_and_p_proxy.py), with Orca `print_host` set to `127.0.0.1:18889`. The helper accepts Orca's `/upload_serial` request, forwards the file to ESP3D's direct-SD `/upload` endpoint, forces uploads into `/up_and_p/`, and rewrites Orca's later `M23` to `/up_and_p/<filename>` before letting `M24` start the print.
- Local desktop startup now goes through [`tools/start_orca_with_esp3d_proxy.py`](/home/fopor/Software/marlin/Marlin-2.1.3-b2/tools/start_orca_with_esp3d_proxy.py), and the user launcher at `~/.local/share/applications/orca.desktop` points to that wrapper instead of directly to the AppImage. The wrapper auto-starts the local proxy when Orca opens and also exposes `--ensure-proxy-only` and `--stop-proxy` management commands.
- On 2026-07-30, Orca arc fitting was enabled in the active `0.20mm Star Standard` process. The firmware already has `ARC_SUPPORT` enabled, so Orca may replace suitable sequences of short linear moves with smaller `G2`/`G3` commands. The main goal is to reduce G-code size and therefore direct-SD upload time, especially for curved models.
- StarGraber is a Cartesian i3-style bedslinger with a full-width horizontal X-rod assembly and a large asymmetric direct-drive carriage. For sequential printing, account for both the entire carriage footprint in XY and finished objects passing beneath the lower X rod as the bed moves in Y; wide X separation alone does not make tall objects safe.
- Conservative physically tested Orca coordinates are `X=0..190` and `Y=5..200`; do not enlarge them from photos or assumptions. Sequential-print carriage clearance radius is provisionally `80 mm` because Orca models the asymmetric carriage as a symmetric nozzle-centered radius. Do not reduce it until the largest nozzle-to-rigid-carriage distance has been physically measured and tested.
- Before enabling Orca `Print Sequence = By Object`, physically measure vertically from the nozzle tip to the lowest surface (not center) of the lowest horizontal X rod, then configure `extruder_clearance_height_to_rod` as that measurement minus `3..5 mm`. Do not use the inherited generic `36 mm` or a photo estimate; photos only suggest the broad `50..60 mm` class. `extruder_clearance_height_to_lid` is `150 mm`, matching usable Z on this open-frame printer, and is not a substitute for rod clearance.
- The active process keeps skirts disabled by inheritance but sets `skirt_type` to per-object for safe future use. `printing_by_object_gcode` is intentionally empty; do not home, probe, tram, generate/load a mesh, or make arbitrary/full-bed parking moves between sequential objects. Initial validation should use two 15--20 mm cubes in an Orca-accepted arrangement, with sliced order/toolpaths inspected and the transition supervised for clearance at the motor, fan/duct, probe, lower rod, and bed clips.
- The toolhead wiring can snag on already completed sequential objects. Required By Object progression is from low Y / high X toward higher Y / lower X (ascending Y, with descending X as the tie-break/directional progression). Orca 2.4.0-beta does not expose a machine-preset coordinate-sorting rule for this; sequential G-code follows the objects' stored `arrange_order`, shown in the viewport as `Sequence #`. Place or auto-arrange first, make separate objects rather than copies grouped as instances when necessary, then drag the objects in the object list into the required order and re-slice. Do not auto-arrange afterward. Verify the numbered sequence and G-code preview before every sequential job. This ordering reduces wire snag risk but does not model the flexible wire as collision geometry or replace securing/routing the wire and supervised validation.
- During helper verification on 2026-03-29, the live ESP3D direct-SD endpoint later started returning `{"status":"No SD Card"}` on `/upload?path=/up_and_p/`, and `M21` did not immediately recover it. End-to-end helper verification was therefore blocked by printer SD availability, not by a local Python startup failure.
- On 2026-07-30, realistic Orca uploads around 1.8 MB reproduced `HTTP 502 Printer upload proxy failed` after about six seconds, while a 154-byte upload succeeded. The cause was the proxy's five-second connect timeout remaining active while `requests`/urllib3 sent the request body; ESP3D can pause socket reads for longer while flushing a large file to SD. The proxy now defaults to a configurable 30-minute upload I/O inactivity timeout (`--upload-timeout`, in seconds) while retaining the short timeout for ordinary commands, and always logs upstream upload exceptions. This timeout is based on a period without socket progress, not total upload duration, so transfers may run longer than 30 minutes if data continues moving.
- Large direct-SD uploads on this TinyBee/ESP3D stack are inherently slow: observed rates are roughly 50–85 KB/s, making a 50 MB G-code transfer take around 10 minutes. Marlin is already using its default `SPI_FULL_SPEED` on ESP32 (16 MHz). ESP3D's synchronous web server receives 1436-byte upload chunks and writes them through Marlin's single-block SPI SD path, so the local proxy is not the primary throughput bottleneck. Raising SD SPI above Marlin's supported default, changing ESP3D buffers, or implementing multi-block/preallocated writes would require a separately tested firmware experiment; do not present those as a risk-free preset change.
- A reusable full calibration program is tracked at [`utility_gcode/stargraber_ubl_calibration.gcode`](/home/fopor/Software/marlin/Marlin-2.1.3-b2/utility_gcode/stargraber_ubl_calibration.gcode). It performs a five-minute heated soak with display progress, homes, runs `G34`, creates and smart-fills the 10x10 UBL mesh, stores it in slot 0, saves EEPROM settings, and parks the printer.

## Known Troubleshooting Context

- Current print issue under investigation: strong stringing on every print.
- Lowering nozzle temperature helps, but stringing is still severe even around `180C` with PLA.
- The same filament prints well on another printer.
- The nozzle has already been changed.
- Extruder grip has already been checked and is good.
- Retraction experiments already tried with no meaningful effect: retraction speed, retraction length, and z-hop on/off.
- Overall print quality is otherwise good.
- Hotend heatsink fan is confirmed strong and always on; it is wired directly to the `300W PSU`.
- Measured hotend/heatsink temperatures during troubleshooting: with the nozzle set to `220C`, the heatsink measured about `36C` at the top, `41C` in the middle, and about `73C` near the last fin close to the block.
- External spot measurement near the nozzle showed about `202C` when the printer reported `220C`, but this should be treated cautiously because surface nozzle readings can under-read depending on measurement method and emissivity.
- Intermittent XY layer shifts were also reported (often on diagonal/high-speed travel). On 2026-04-03, the chosen first response was a moderate slicer-only reduction (not aggressive), keeping Marlin firmware upper bounds unchanged: `StarGraber` machine XY max speed set to `300`, machine XY max acceleration set to `2500`, start G-code changed from `M204 S10000 T1000` to `M204 P1500 T1200`, and `0.20mm Star Standard` reduced to `travel_speed 240`, `travel_acceleration 1400`, `inner_wall_acceleration 1300`, `outer_wall_acceleration 800`.
- On 2026-07-26, a single Y-axis (bed-carriage) step skip occurred only after many hours of printing. As a conservative Orca-only response, `0.20mm Star Standard` travel acceleration was reduced from `4000` to `3600` mm/s²; firmware limits were left unchanged. If it recurs, also investigate Y motor/driver heat, belt tension and pulley grub screws, wheel/bearing drag, and any intermittent nozzle collision.
- On 2026-07-04, the user reported intermittent second-print homing where Z appears to home before X/Y without restarting the printer, risking a Z crash if the probe is off the bed. Current config has `Z_SAFE_HOMING` enabled and `HOME_Z_FIRST` disabled. Orca `StarGraber` start G-code previously contained both `G28` and a later `G28 Z`; the later `G28 Z` was removed to avoid a Z-only home/probe path being reached before a fresh XY home.
- On 2026-07-29, the active `StarGraber` start G-code was tightened up: it resets speed and flow overrides, uses a one-minute display sequence still named `Soak`, waits for the nozzle to reach the `160C` probing temperature before `G28`, and starts purging deterministically at `X5 Y2`. The purge remains on the existing front service line, stops at the firmware-safe `X185`, and feeds `45mm` total instead of `59.5mm`; about `35mm` of that restores the filament retracted by the active end G-code.
- Later on 2026-07-29, the user reported that probing during the new start sequence nearly caused a crash. The configured `G28` safe-home point places the probe at `(105,100)` and the nozzle at `(84,117)` with offset `{ 21, -17, -1.93 }`, so that point is geometrically safe. The following UBL `G29 J` is more suspect if the event occurred near an edge: its calculated probe points are approximately `(20,20)`, `(190,20)`, and `(105,180)`, corresponding to nozzle positions `(-1,37)`, `(169,37)`, and `(84,197)`. Confirm which move caused the event before changing firmware or start G-code.
- A subsequent retry of the same print start sequence completed normally. It is safe to print immediately after `stargraber_ubl_calibration.gcode` has fully completed: the calibration saves UBL slot 0, turns off the heaters, and parks with `G27`; the print then performs a fresh `G28`, loads the newly saved slot, and applies `G29 J`. Wait for the `Calibration saved` display message and for calibration motion to stop before starting the print; do not send upload-and-print while the calibration SD job is still active.
